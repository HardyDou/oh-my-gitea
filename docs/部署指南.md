# Docker 部署与 Gitea 配置

## 文件说明

| 文件 | 用途 |
| --- | --- |
| `Dockerfile` | Node.js 22 多阶段构建后端，以非 root 用户运行 |
| `web/Dockerfile` | 构建 Vue 页面，使用 Nginx 1.28 提供静态资源和代理 |
| `web/nginx.conf` | SPA 路由回退及 `/api/`、`/auth/`、`/webhooks/`、`/health` 代理 |
| `docker-compose.deploy.yml` | 完整部署：PostgreSQL、后端、前端 |
| `docker-compose.yml` | 本地开发：仅 PostgreSQL，绑定本机 5432 端口 |
| `.env.docker.example` | 容器部署变量模板 |

需要 Docker Engine / Docker Desktop、Docker Compose v2，以及 Docker Hub 和 npm 网络访问。构建不会复制 `.env`、本地密钥和数据库备份。

## 一、启动

```bash
git clone https://github.com/HardyDou/oh-my-gitea.git
cd oh-my-gitea
cp .env.docker.example .env.docker
chmod 600 .env.docker
```

编辑 `.env.docker`，设置 `POSTGRES_PASSWORD`（数据库密码，推荐较长的字母数字组合，避免连接 URL 中的特殊字符）。其余配置可先保留示例值。

**不需要生成或填写 32 位管理密钥。管理员密码在首次打开页面时自己设置。** 新部署的底层加密密钥由系统自动生成，并持久化到后端数据卷。

```bash
docker compose --env-file .env.docker -f docker-compose.deploy.yml config --quiet
docker compose --env-file .env.docker -f docker-compose.deploy.yml up -d --build
docker compose --env-file .env.docker -f docker-compose.deploy.yml ps
curl http://localhost:8080/health
```

打开 <http://localhost:8080>。

- 默认仅监听 `127.0.0.1:8080`。**必须先在本机或可信网络设置管理员密码，再向公网开放服务**，否则第一个访问者可能抢先成为管理员。
- 数据库和后端不暴露宿主机端口。启动顺序为数据库健康 → 后端健康 → 前端。
- PostgreSQL 首次创建空数据卷时按文件名顺序执行 `db/*.sql`。
- `/health` 只表示后端存活，不代表 Gitea 可访问；`/nginx-health` 只检查 Nginx。
- 不带 `--quiet` 的 `docker compose config` 会输出解析后的数据库密码，不要把输出公开。

## 二、在页面设置管理员密码和 Gitea

1. 打开 **系统配置 → Gitea 集成**。
2. 首次使用填写两次管理员密码，至少 8 位（最多 128 位），建议混合字母、数字和符号。**没有公共默认密码**。这是本系统的配置管理密码，不是 Gitea 密码。
3. 后续修改配置时输入这个密码即可。密码仅以随机盐 + scrypt 哈希保存，不保存明文；管理员会话为 30 分钟，点击“退出管理”立即失效。
4. 在 Gitea“设置 → 应用”中创建 OAuth2 应用，将配置页显示的回调地址原样填入：
   - 本机容器部署：`http://localhost:8080/auth/gitea/callback`
   - 正式部署：`https://pm.example.com/auth/gitea/callback`
5. 填写 Gitea 地址、Client ID、Client Secret；公共 OAuth 客户端可不填 Client Secret。
6. 不使用 Webhook 时可留空，未设置 Webhook 密钥时接收接口禁用，不影响登录。
7. 保存后切换工作台，点击“登录 Gitea”完成授权。

### 行为说明

- 保存 Gitea 配置会清除已有 Gitea 登录会话及待完成的 OAuth 请求，不会退出当前管理员配置会话。
- 管理员密码只授权管理 Gitea 集成配置，不授予 Gitea 仓库访问权限。
- Gitea Secret 使用 AES-256-GCM 加密存库。读取接口仅返回“是否已配置”，不回显密钥。修改时留空保留原值，暂不提供清空已保存密钥的按钮。
- 保存不测试连通性或 OAuth 凭据，需要实际登录验证。容器必须能访问 Gitea，不要把宿主机上的服务填为容器自己的 `localhost`。
- 回调地址由 `APP_URL` 决定；更换域名需同步修改环境变量和 Gitea OAuth 应用。
- 已有用户或仓库数据后，禁止直接更换 Gitea 地址，防止不同实例数字 ID 冲突。实例迁移需另行处理数据。
- 数据库中的配置优先于旧的 `GITEA_*` 环境变量；从旧环境变量迁移时，先保留原值，在页面读取并保存即可。
- 旧版 `SYSTEM_CONFIG_TOKEN` 已停用，不再接受该请求头解锁配置。升级后首次访问配置页设置管理员密码即可。
- 初始化和登录接口按后端所见 IP 限制尝试次数（15 分钟最多 10 次，成功登录后清零）。反向代理后的访问可能共用限额；正式部署应在可信代理层进一步限制请求。
- Webhook 仍沿用 `X-Gitea-Token` 校验，不会自动注册 Webhook；标准 Gitea `X-Gitea-Signature` 原始请求体签名仍需适配验证。

## 三、HTTPS 正式部署

完成首次管理员设置后，在宿主机使用 Caddy / Nginx 终止 TLS。例如 Caddy：

```caddyfile
pm.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

域名指向服务器，开放 80/443 端口，修改 `.env.docker`：

```dotenv
APP_URL=https://pm.example.com
HTTP_BIND=127.0.0.1
HTTP_PORT=8080
SESSION_COOKIE_SECURE=true
```

重新执行 `up -d --build`，同步更新 Gitea OAuth 回调。公网不得通过 HTTP 传输管理员密码或 OAuth 凭据。若外层代理也在容器中，需加入相同 Docker 网络并访问 `web:80`，不能使用代理容器自己的 `127.0.0.1`。

## 四、加密密钥与数据卷

| 数据 | 保存位置 |
| --- | --- |
| 管理员密码哈希、Gitea 配置密文和业务数据 | PostgreSQL 的 `pm-deploy-postgres` 卷 |
| 自动生成的配置加密密钥 | `pm-backend-data` 卷中的 `session-secret`，容器路径 `/app/data/session-secret` |
| 本地开发自动生成的密钥 | `.data/session-secret`（已被 Git 忽略） |

**数据库和加密密钥必须一起备份。** 密码哈希与加密密钥用途不同，重置管理员密码不会自动更换配置加密密钥。

如果旧部署已有 `SESSION_SECRET`，升级时必须保留原值；不要直接改为空或替换，否则已有 Gitea 配置无法解密。仅新部署可留空自动生成。系统不会在每次启动时更换已有密钥；丢失密钥后无法从密文恢复 Secret。

`pm-deploy-postgres` 与开发用 `pm-postgres` 是独立卷，不会自动导入开发数据。数据库密码在首次初始化后不会随环境变量自动变化，轮换需同步修改 PostgreSQL 中的密码。

## 五、运维与备份

```bash
# 更新并重建
git pull --ff-only
docker compose --env-file .env.docker -f docker-compose.deploy.yml up -d --build

# 日志
docker compose --env-file .env.docker -f docker-compose.deploy.yml logs --tail=100 -f backend web

# 数据库及自动生成的密钥备份；backups/ 已被 Git 忽略
umask 077
mkdir -p backups
docker compose --env-file .env.docker -f docker-compose.deploy.yml exec -T postgres \
  pg_dump -U pm -d gitea_pm > backups/gitea-pm.sql
docker compose --env-file .env.docker -f docker-compose.deploy.yml cp \
  backend:/app/data/session-secret backups/session-secret
chmod 600 backups/session-secret

# 停止，不删除数据卷
docker compose --env-file .env.docker -f docker-compose.deploy.yml down
```

若使用旧环境变量 `SESSION_SECRET`，容器内可能没有密钥文件，此时需安全备份 `.env.docker` 中的原值，而不是执行文件复制。备份不要公开或提交到 GitHub。

恢复时先停止后端写入，将 SQL 备份导入由管理员准备的**空数据库**，再恢复原密钥（文件所有者需允许容器的 node 用户读取，权限 600）或原 `SESSION_SECRET`，最后启动服务。默认 Compose 会自动建表，不能把完整 SQL 备份直接导入已初始化的库。

**不要执行 `down -v`，会删除数据库和加密密钥数据卷。**

### 忘记管理员密码

目前没有邮件找回。服务器管理员需先关闭公网访问并停止后端，在数据库中删除 `system_administrator` 的单行记录，再重启后端并立即在可信环境设置新密码。不要删除 Gitea 配置、业务表或加密密钥。重启会同时作废旧管理员会话；请务必完成重设后再开放公网。

### 已有数据库及限制

- 初始化 SQL 只对空卷执行。当前后端会补建阶段配置、系统配置和管理员表，基础业务表仍须由 `001_init.sql` 创建；新版本迁移前必须备份，不能假定重建容器会重放全部 SQL。
- Gitea 会话、管理员会话、登录限流和 OAuth 临时状态存在内存中，重启需重新登录，暂不支持多后端副本。
- 阶段配置还没有独立管理员角色；当前原型并未完成所有生产安全加固。
- 写入 Issue 取决于 Gitea 真实权限及 OAuth `write:issue` 范围。
- Nginx 请求体限制为 21 MiB，后端单附件限制为 20 MiB。
