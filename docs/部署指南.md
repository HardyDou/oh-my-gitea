# Docker 部署与 Gitea 配置

## 文件说明

| 文件 | 用途 |
| --- | --- |
| `Dockerfile` | Node.js 22 多阶段构建后端，运行阶段仅安装生产依赖并以非 root 用户启动 |
| `web/Dockerfile` | 构建 Vue 静态资源，由 Nginx 1.28 提供页面及反向代理 |
| `web/nginx.conf` | SPA 路由回退；代理 `/api/`、`/auth/`、`/webhooks/`、`/health` |
| `docker-compose.deploy.yml` | 完整部署：PostgreSQL、后端、前端 |
| `docker-compose.yml` | 本地开发：仅 PostgreSQL，绑定本机 5432 端口 |
| `.env.docker.example` | 容器部署环境变量模板，不包含 Gitea 凭据 |

依赖 Docker Engine / Docker Desktop 和 Docker Compose v2。镜像从 Docker Hub 拉取，依赖通过 npm 安装，需要访问这些服务。镜像构建不会复制 `.env` 文件；生产密钥只在容器运行时传入。

## 一、准备部署环境

```bash
git clone https://github.com/HardyDou/oh-my-gitea.git
cd oh-my-gitea
cp .env.docker.example .env.docker
chmod 600 .env.docker

# 分别执行三次，将结果填入下面对应字段。
openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32
```

编辑 `.env.docker`：

- `POSTGRES_PASSWORD`：数据库密码，推荐直接使用生成的十六进制字符串；此值会拼入连接 URL，不要使用未经 URL 编码的特殊字符。
- `SESSION_SECRET`：至少 32 位的独立随机密钥，用于会话签名和 Gitea 配置加密。
- `SYSTEM_CONFIG_TOKEN`：至少 32 位的独立管理密钥，用于解锁配置页面，**不要交给普通用户**。
- `APP_URL`：用户浏览器访问地址，不带末尾 `/`，例如 `http://localhost:8080`。
- `HTTP_BIND` / `HTTP_PORT`：默认只监听 `127.0.0.1:8080`。
- `SESSION_COOKIE_SECURE`：本机 HTTP 试用设为 `false`；HTTPS 正式部署必须为 `true`。

Gitea 地址、OAuth Client ID、Client Secret 和 Webhook 密钥均在页面中配置，不必写进部署文件。

## 二、启动

```bash
docker compose --env-file .env.docker -f docker-compose.deploy.yml config --quiet
docker compose --env-file .env.docker -f docker-compose.deploy.yml up -d --build
docker compose --env-file .env.docker -f docker-compose.deploy.yml ps
curl http://localhost:8080/health
```

打开 <http://localhost:8080>。首次部署会进入系统配置页。

启动顺序为数据库健康 → 后端健康 → 前端。PostgreSQL 首次创建空数据卷时，按文件名顺序执行 `db/*.sql`。数据库和后端不向宿主机暴露端口。

`/health` 是后端存活检查，不表示 Gitea 已连通；`/nginx-health` 仅检查静态站点服务。

> `docker compose config` 不带 `--quiet` 会输出解析后的密钥，不要把输出粘贴到公开日志或 Issue。

## 三、在页面配置 Gitea

1. 打开 **系统配置 → Gitea 集成**。
2. 输入 `.env.docker` 中的 `SYSTEM_CONFIG_TOKEN`，点击“解锁配置”。不依赖 Gitea 登录，避免首次安装或 OAuth 配置错误时无法修复。
3. 在 Gitea 的“设置 → 应用”中创建 OAuth2 应用。将页面显示的回调地址原样填入：
   - 本机容器部署：`http://localhost:8080/auth/gitea/callback`
   - 正式部署：`https://pm.example.com/auth/gitea/callback`
4. 填写 Gitea 地址、Client ID、Client Secret。公共 OAuth 客户端允许无 Client Secret，机密客户端应填写。
5. 用 `openssl rand -hex 32` 另行生成 Webhook 密钥并填写。
6. 保存后切换到工作台，点击“登录 Gitea”完成授权。所有已有浏览器会话会失效，需重新登录。

注意：

- 密钥以 AES-256-GCM 加密保存到 PostgreSQL 的 `system_settings` 表，接口只返回“是否已配置”，不返回明文。
- 修改时密钥留空表示保留旧值；目前不提供清空已保存密钥的操作。
- 管理密钥只保存在页面内存中，锁定、离开组件或刷新后需重新输入。
- 回调地址由 `APP_URL` 推导，属于本系统部署地址，而不是 Gitea 实例配置。更换域名需修改 `APP_URL`、重建容器并同步修改 Gitea OAuth 应用。
- 保存不验证 Gitea 连通性或 OAuth 凭据，需实际登录验证；容器必须能访问 Gitea，不能把宿主机上的 Gitea 填为容器内的 `localhost`。
- 已有用户或仓库数据时禁止直接修改 Gitea 地址，防止不同实例数字 ID 冲突。迁移实例需要独立部署或另行规划数据迁移。
- 数据库中的 Gitea 配置优先于旧的 `GITEA_*` 环境变量。原有环境变量仍可作为未保存配置时的兼容来源。
- **不能直接轮换或丢失 `SESSION_SECRET`**：更换后无法解密已有配置。迁移时必须同时保留数据库和原密钥；管理密钥 `SYSTEM_CONFIG_TOKEN` 可单独轮换，重建后端生效。
- 当前 Webhook 接收接口沿用 `X-Gitea-Token` 校验，未设置密钥时拒绝请求。此配置不会自动注册 Webhook，也不代表已实现 Gitea `X-Gitea-Signature` 原始请求体签名校验；使用标准 Gitea Webhook 前仍需适配与验证。

## 四、HTTPS 正式部署

建议在宿主机使用 Caddy / Nginx 终止 TLS，并代理到 `127.0.0.1:8080`。例如 Caddy：

```caddyfile
pm.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

将域名 DNS 指向服务器，开放 80/443 端口，然后修改 `.env.docker`：

```dotenv
APP_URL=https://pm.example.com
HTTP_BIND=127.0.0.1
HTTP_PORT=8080
SESSION_COOKIE_SECURE=true
```

重新执行 `up -d --build`，并同步更新 Gitea OAuth 回调。公网不应使用 HTTP 传输管理密钥或 OAuth 凭据。若反向代理也运行在容器中，不能使用其自身的 `127.0.0.1` 访问此服务，应连接相同 Docker 网络并代理到 `web:80`。

## 五、升级、日志与备份

```bash
# 更新并重建
git pull --ff-only
docker compose --env-file .env.docker -f docker-compose.deploy.yml up -d --build

# 查看日志
docker compose --env-file .env.docker -f docker-compose.deploy.yml logs --tail=100 -f backend web

# 备份数据库（含配置密文、用户信息及审计记录，妥善保管）
umask 077
docker compose --env-file .env.docker -f docker-compose.deploy.yml exec -T postgres \
  pg_dump -U pm -d gitea_pm > gitea-pm-backup.sql

# 停止，不删除数据卷
docker compose --env-file .env.docker -f docker-compose.deploy.yml down
```

另外安全备份 `.env.docker`，特别是 `SESSION_SECRET`。数据库备份文件不要提交到 GitHub。

恢复前先停止后端写入；将备份恢复到一个**空数据库**（不要覆盖正在使用的数据库）：

```bash
docker compose --env-file .env.docker -f docker-compose.deploy.yml exec -T postgres \
  psql -U pm -d gitea_pm -v ON_ERROR_STOP=1 < gitea-pm-backup.sql
```

上面的恢复命令仅适用于已准备好的空库。默认 Compose 首次启动会自动建表，因此恢复前需由管理员备份并准备独立空库，不能直接向已初始化的库导入完整 SQL 备份。

**不要使用 `down -v`，它会删除数据库卷。** 修改 `.env.docker` 中的数据库密码不会更改已初始化数据库的密码，需要另行执行数据库密码轮换并同步配置。

完整部署使用 `pm-deploy-postgres` 卷，与本地开发的 `pm-postgres` 分开，不会自动导入原有开发数据。迁移数据请使用备份/恢复流程，且保留原 `SESSION_SECRET`。

### 已有数据库

`docker-entrypoint-initdb.d` 只对空数据卷执行。当前后端启动时会确保阶段配置和系统配置表存在；原型的基础表仍须由 `001_init.sql` 创建。对已有数据库执行 SQL 前应备份；后续增加新迁移时需要按对应版本说明显式执行，不能假定重建容器会自动重放 SQL。

### 当前限制

- 登录会话和 OAuth 临时状态仍保存在后端内存，重启会退出登录，暂不支持多后端副本部署。
- Gitea 配置在单进程中热更新；外部直接改库不会自动通知后端。
- 阶段配置尚未实现独立管理员角色；不要把当前原型视为已完成生产安全加固。
- Issue 写入仍取决于真实 Gitea 权限及 OAuth `write:issue` 范围。
- Nginx 请求体限制为 21 MiB，后端单附件限制为 20 MiB。
