# Gitea PM 功能清单与业务规则

版本：v0.1

> 本文定义“系统有哪些模块、每个模块做什么、具体遵循什么规则”，作为 MVP 开发依据。
>
> 重要模型：一个 Gitea 仓库下可以有多个 Gitea 原生 Project；本系统不重新创建项目，只为 Gitea Issue 增加阶段和优先级。

## 1. 系统登录模块

### 功能

- Gitea OAuth2 登录
- 兼容 Gitea 现有 SSO
- 当前用户信息展示
- 登出
- 会话过期处理

### 规则

1. 系统不保存 Gitea 密码。
2. 用户首次登录后创建本地用户映射，使用 `gitea_user_id` 作为唯一标识。
3. Gitea 未授权或账号无效时，禁止进入系统。
4. 浏览器用户使用 OAuth 会话。
5. Agent 使用 Gitea Personal Access Token 或 OAuth Access Token 调用 API。

## 2. 仓库模块

### 功能

- 获取当前用户可访问的 Gitea 仓库
- 仓库切换
- 查看仓库基本信息
- 查看仓库同步状态

### 规则

1. 仓库列表以 Gitea API 返回结果为准。
2. 用户只能看到自己在 Gitea 中有访问权限的仓库。
3. 系统不直接读取 Gitea 数据库。
4. 仓库是 Issue 原始数据的归属范围，不直接等同于本系统项目。
5. 暂不支持跨仓库统一看板。

## 3. Gitea Project 维度模块

### 功能

- 查询仓库下的 Gitea 原生 Project
- 按 Project 筛选 Issue
- 展示 Project 名称、状态和所属仓库
- 同步 Project 与 Issue 的关联关系

### 规则

1. Project 由 Gitea 创建、修改和归档，本系统只读使用。
2. 一个 Gitea 仓库可以拥有多个 Gitea Project。
3. 本系统不建立独立的项目实体，不提供本地项目 CRUD。
4. 一个 Issue 可以属于多个 Gitea Project。
5. Project 只是 Issue 的筛选维度，不决定 Issue 的阶段和优先级。

## 4. Issue 同步模块

### 功能

- 首次全量同步 Issue
- Webhook 实时同步
- 定时校准同步
- 同步失败重试
- 同步事件记录

### 规则

1. Issue 标题、描述、评论、负责人、状态、标签等原始信息以 Gitea 为准。
2. Gitea 是 Issue 原始数据的唯一来源。
3. 首次访问仓库时创建或更新 Issue、Project 及其关联记录。
4. Webhook 负责处理 Issue 创建、修改、关闭、重新打开、标签和负责人变化。
5. 定时任务用于补偿 Webhook 丢失、重复或处理失败的事件。
6. Webhook 必须校验 Secret，并按 Delivery ID 做幂等处理。
7. Gitea 删除 Issue 时，本系统保留管理记录和流转历史，只标记原 Issue 不可用。
8. Issue 的 Gitea 状态与本系统阶段相互独立，不自动将关闭映射为“完成”。

## 5. Issue 管理模块

### 功能

- 按 Gitea Project 筛选 Issue
- 展示 Issue 所属 Gitea Project
- Issue 详情
- 跳转 Gitea 原始 Issue
- 查看原始信息
- 管理阶段
- 管理优先级
- 查看流转历史

### 本系统字段

| 字段 | 可选值 | 默认值 | 数据来源 |
|---|---|---|---|
| 阶段 | 需求、研发、测试、完成 | 需求 | 本系统 |
| 优先级 | P0、P1、P2、P3 | P2 | 本系统 |
| 类型 | 需求、缺陷等 | 读取 Gitea Issue 类型 | Gitea |

### 规则

1. 阶段和优先级只存储在本系统，不修改 Gitea 原始 Issue。
2. 一个 Gitea Issue 只对应一套本系统阶段和优先级。
3. Issue 所属多个 Gitea Project 时，阶段和优先级不随 Project 分裂。
4. 新发现但尚未管理的 Issue，显示默认阶段“需求”、默认优先级“P2”。
5. Issue 原始标题、描述、评论等在本系统只读展示。
6. 详情页必须显示 Gitea 当前状态、所属 Project 和原始链接。
7. Issue 被 Gitea 删除后不能继续修改，但历史记录仍可查看。

## 6. 看板模块

### 功能

- 四列看板
- Issue 卡片
- 拖拽流转
- 点击查看详情
- 看板统计
- 空列提示
- 多条件组合筛选
- 排序

### 看板列

```text
需求 → 研发 → 测试 → 完成
```

### 卡片显示规则

每张卡片至少显示：

- Issue 编号
- Issue 标题
- 优先级
- Issue 类型
- Gitea 状态
- 负责人
- 最近更新时间

### 筛选规则

支持以下条件，并允许组合筛选：

| 筛选条件 | 数据来源 |
|---|---|
| 更新时间区间 | Gitea Issue `updated_at` |
| 仓库 | Gitea 仓库 |
| Project | Gitea 原生 Project |
| 阶段 | 本系统 |
| 优先级 | 本系统 |
| 标签 | Gitea Label |
| 里程碑 | Gitea Milestone |
| 作者 | Gitea Issue 作者 |
| 被指派人 | Gitea Assignee |
| 类型 | Gitea Issue 类型 |
| 关键词 | Gitea Issue 编号、标题 |

排序支持按更新时间、创建时间、编号，分别支持升序和降序。筛选和排序只影响当前视图，不修改数据。

## 7. 我的任务模块

### 功能

- 查看当前登录用户被 Gitea 指派的 Issue
- 跨当前用户可访问仓库和 Project 汇总
- 按阶段、优先级、更新时间筛选
- 点击进入 Issue 详情
- 直接修改阶段和优先级

### 规则

1. “我的任务”是一个固定的负责人筛选视图，不是独立数据表。
2. 默认条件为 `assignee = 当前 Gitea 用户`。
3. Issue 的负责人以 Gitea Assignee 为准。
4. 只有当前用户有仓库访问权限的 Issue 才能展示。
5. Agent 不使用“我的任务”视图，Agent 通过负责人参数查询。

## 8. 阶段流转模块

### 功能

- 详情页修改阶段
- 看板拖拽修改阶段
- 测试退回研发
- 查看阶段变化记录

### 默认流转规则

四个阶段之间可以任意切换：

```text
需求 ↔ 研发 ↔ 测试 ↔ 完成
```

也允许直接从任意阶段切换到其他阶段。

### 具体规则

1. 阶段可以直接变更到任意其他阶段，不限制跳转顺序。
2. 阶段不变时不产生流转记录。
3. 每次阶段变化必须记录：Issue、操作人、操作来源、原阶段、新阶段、时间。
4. 看板拖拽、卡片快捷操作和 API 修改必须使用同一套更新逻辑。
5. 阶段流转不自动关闭或重新打开 Gitea Issue。

## 9. 优先级模块

### 优先级定义

| 优先级 | 含义 |
|---|---|
| P0 | 阻断生产或核心功能不可用，立即处理 |
| P1 | 高优先级，影响主要功能或当前迭代 |
| P2 | 普通需求或缺陷，默认优先级 |
| P3 | 低优先级、优化类或暂不紧急事项 |

### 规则

1. 用户可以将 Issue 修改为任意优先级。
2. 优先级修改不改变阶段。
3. 优先级变化必须记录操作人、原值、新值和时间。
4. P0 仅做醒目标识，初版不增加额外审批和权限限制。

## 10. 权限模块

### 功能

- 读取 Gitea 仓库权限
- 校验 Issue 查询权限
- 校验管理字段修改权限

### 规则

1. 不建立复杂的本地角色系统。
2. 有 Gitea 仓库读取权限：可以查看项目和 Issue。
3. 有 Gitea 仓库写权限：可以修改阶段和优先级。
4. 无 Gitea 仓库权限：接口返回无权限，不返回 Issue 数据。
5. Agent 使用的 Token 对应一个 Gitea 用户，权限规则与普通用户一致。
6. 所有修改都记录实际 Gitea 用户和操作来源（用户/Agent）。

## 11. Agent API 模块

### 功能

- 查询可访问仓库
- 查询 Issue 列表和详情
- 按阶段、优先级和状态筛选
- 修改阶段
- 修改优先级
- 查询流转历史

### API 规则

1. 使用 `Authorization: Bearer <gitea-token>`。
2. Agent Token 不保存到本系统数据库，也不能出现在日志和 URL 中。
3. 每次请求都根据 Token 识别 Gitea 用户并校验仓库权限。
4. 写操作必须校验阶段流转规则和仓库写权限。
5. 写操作支持 `Idempotency-Key`，Agent 重试不得产生重复变更。
6. 所有接口返回稳定的 JSON 结构和明确错误码。
7. 所有 Agent 写操作必须写入审计日志。

### 初始接口

```text
GET   /api/v1/repositories
GET   /api/v1/repositories/:owner/:repo/projects
POST  /api/v1/repositories/:owner/:repo/projects
GET   /api/v1/repositories/:owner/:repo/projects/:projectKey/issues
POST  /api/v1/repositories/:owner/:repo/projects/:projectKey/issues/:number
GET   /api/v1/repositories/:owner/:repo/projects/:projectKey/issues/:number
PATCH /api/v1/repositories/:owner/:repo/projects/:projectKey/issues/:number/management
DELETE /api/v1/repositories/:owner/:repo/projects/:projectKey/issues/:number
GET   /api/v1/repositories/:owner/:repo/projects/:projectKey/issues/:number/history
```

## 12. 审计与操作记录模块

### 功能

- 阶段修改记录
- 优先级修改记录
- Agent 操作记录
- Webhook 事件记录
- 同步失败记录

### 规则

每条管理变更至少记录：

- 操作人 Gitea User ID
- 操作类型：用户或 Agent
- 操作动作
- 目标仓库和 Issue
- 修改前数据
- 修改后数据
- 请求 ID
- 操作时间

审计记录只追加，不允许通过普通业务接口修改或删除。

## 13. 系统配置模块

### v0.1 配置

通过环境变量配置：

- Gitea 地址
- Gitea OAuth Client ID
- Gitea OAuth Client Secret
- OAuth 回调地址
- Webhook Secret
- PostgreSQL 连接地址
- 前端访问地址

### 规则

1. v0.1 只支持连接一个 Gitea 实例。
2. 配置不提供前端修改页面。
3. Secret 不写入日志和接口响应。
4. 后续再增加多 Gitea 实例管理。

## 14. v0.1 不包含的功能

- 本地复杂角色、审批流和组织权限
- 跨仓库统一看板
- 独立评论系统
- 测试用例管理
- 版本发布和自动部署
- 通知中心、邮件、即时通讯通知
- 工时统计和复杂报表
- Gitea Issue 原始内容编辑
